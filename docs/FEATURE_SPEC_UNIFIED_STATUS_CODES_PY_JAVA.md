# Feature Spec: Unified Status Codes Across Python and Java (V1)

## Purpose

Define a single, explicit status-code contract used consistently across:

- Python CLI/tooling (`tools/can_nt/...`)
- Java robot command handling (`src/main/java/...`)

Goal: remove ambiguity from mixed status styles (`ok/error` text vs encoded codes), while preserving safe backward compatibility during rollout.

## Status

Draft V1 (planning only).

No implementation changes are approved by this spec alone.

## Background

Current behavior is mixed:

- Python code paths mostly use encoded status codes (`SEV/FAC/MSG`) via `StatusResult`.
- Java command responses commonly expose `status: "ok"|"error"` and free-text messages.

This creates inconsistent machine behavior, harder regression validation, and uneven operator diagnostics.

## Problem Statement

Without one cross-language status-code model:

- equivalent failures can look different between host and robot paths
- scripts cannot reliably assert on one stable field
- parsing logic becomes branch-heavy and fragile
- dashboards and logs lose precise failure categorization

## Goals

- One canonical encoded status-code model across Python and Java command surfaces.
- Keep existing text fields during migration to avoid breaking consumers.
- Make status output deterministic for regression and CI.
- Maintain clear human-readable details while machine logic keys off codes.

## Non-Goals

- Replacing all human-readable message strings.
- Redesigning command semantics.
- Changing NetworkTables key hierarchy beyond what this spec explicitly defines.
- Removing compatibility fields in V1.

## Core Contract

### Canonical Outcome Field

All command responses must include a canonical numeric `code` field.

- `code` is the authoritative machine field.
- `status` string remains compatibility/UI-oriented in V1.
- `message`/`detail` remain human-readable diagnostics.

### Required Response Shape

For command acknowledgements/results (TCP and mirrored NT surfaces where applicable):

- `code` (integer, required)
- `status` (string, required in V1 compatibility phase)
- `message` (string, optional but recommended)
- `detail` (string/object optional)

### Status Semantics

- Success/failure determination must derive from `code` severity, not text status.
- `status` string must be derived from `code` consistently in V1 (`success`, `warning`, `error` mapping defined below).

## Code Model

### Encoding Model

Use the same conceptual model in both languages:

- severity (`SEV`)
- facility (`FAC`)
- message id (`MSG`)

The encoded integer format must match between Python and Java.

SID_QUESTION: Should Java import an autogenerated constants artifact from Python sources, or should both languages generate from one shared schema file?

### Severity Mapping

Normative mapping for V1 compatibility `status` text:

- success -> `status: "ok"`
- warning -> `status: "warning"`
- error -> `status: "error"`

If legacy consumers only recognize `ok/error`, warning may be represented as `error` on legacy-only keys, but canonical payload must retain warning severity in `code`.

## Surfaces in Scope

### Python Scope

- CLI stdout structured status lines (already largely compliant)
- TCP/NT client handling paths consuming robot acks/results
- regression scripts and parsers that currently inspect text-only status

### Java Scope

- UI command ACK payload generation
- UI command OUT/result payload generation
- robot-side command execution result plumbing
- optional NT mirror entries for command outcomes

### Out-of-Scope Surfaces (V1)

- unrelated telemetry streams with no command outcome semantics
- historic archived log files

## Backward Compatibility

### Compatibility Window

V1 requires dual-field emission:

- canonical `code` always present
- legacy `status` string retained

No immediate removal of `status` in V1.

### Consumer Behavior Rules

- New consumers must prefer `code`.
- Existing consumers may continue reading `status` during migration.
- If both are present and conflict, `code` wins.

## Error Taxonomy and Ownership

### Facilities

Facilities must remain stable and cross-language aligned (examples):

- CLI_PARSER
- CLI_VALIDATOR
- EXECUTOR
- NETWORK
- CONFIG
- DEVICE
- GROUP
- INPUT_BINDING

Adding new facilities requires:

- shared declaration update
- Python and Java constant regeneration/update
- mapping update in documentation

### Message IDs

Message IDs must be stable identifiers; text messages may evolve.

No behavior should depend on message text content.

## Serialization Contract

### ACK Payload (Normative Example)

```json
{
  "type": "ack",
  "seq": 41,
  "name": "showStatus",
  "code": 196616,
  "status": "ok",
  "message": "Success.",
  "ts": 1713748800.123,
  "sessionId": "abc123"
}
```

### Error Example

```json
{
  "type": "ack",
  "seq": 42,
  "name": "groupDelete",
  "code": 524307,
  "status": "error",
  "message": "group \"active\" cannot be deleted"
}
```

## Java Rollout Requirements (Design)

Purpose: define expected architecture before implementation.

- Introduce Java-side status-code model mirroring Python encode/decode semantics.
- Route command handlers to return structured status objects, not just booleans.
- Emit canonical `code` in ACK/OUT payloads.
- Derive `status` text from `code` severity.
- Keep existing human message fields intact.

SID_COMMENT: Prefer central encode/decode utility in Java to avoid per-handler ad hoc mappings.

## Python Rollout Requirements (Design)

Purpose: ensure consumers and tests standardize on codes.

- Ensure Python robot-response parsing reads `code` first.
- Preserve current display formatting but source from canonical code path.
- Update regression scripts to assert code-based outcomes where available.

## NetworkTables Considerations

If command outcomes are mirrored into NT keys:

- include integer code key (for machine checks)
- keep legacy status/message keys in V1
- document any added keys in NT contract docs

## Logging and Observability

- Logs should include `code` and decoded symbolic label where possible.
- Human detail text remains required for operator triage.
- Avoid relying on full-text matching in automated regressions.

## Regression Strategy

### Required Test Classes

1. Python local command-path regressions (code assertion first)
2. Robot non-motion connected regressions (code presence and semantic correctness)
3. Cross-path equivalence tests for representative errors/successes

### Minimum Verification Matrix

- success path (e.g., show status)
- parser/validator error
- config error
- device/group not found
- network not connected

For each row, assert:

- canonical `code` present
- severity-consistent `status`
- stable facility/message id mapping

## Migration Plan (Phased)

### Phase 0: Contract Freeze

- finalize shared encoding spec
- freeze initial facility/message catalog for migration set

### Phase 1: Java Dual Emission

- add `code` to Java ACK/OUT while retaining legacy fields
- no consumer-breaking changes

### Phase 2: Python Consumer Preference

- Python readers/runners prefer `code`
- keep fallback to `status` for transitional paths only

### Phase 3: Regression Gate

- require code assertions in primary regression suites
- treat missing `code` as failure on migrated command paths

### Phase 4: Compatibility Review

- review adoption metrics
- decide when/if to relax/remove legacy status dependence

## Definition of Done (V1)

- Canonical `code` field present on all in-scope Java command outcomes.
- Python command consumers parse and prioritize `code`.
- Regression suites include explicit code assertions for local and robot non-motion paths.
- Documentation updated with code contract and compatibility behavior.

## Risks

- Partial rollout can create mixed behavior if handlers are missed.
- Divergent constants between languages can cause silent misclassification.
- Legacy consumers may mis-handle warning semantics.

## Mitigations

- central shared constants source or generation workflow
- automated parity check between Python and Java code tables
- strict regression checks for `code` presence and decode consistency

## Tradeoffs

- Dual-field compatibility increases payload size and maintenance, but avoids abrupt breaks.
- Strict code-first regressions improve reliability, but require upfront migration discipline.
- Shared generation tooling adds complexity, but reduces long-term drift risk.

## Future Extensions

- Full schema versioning for command response payloads.
- Auto-generated docs for facility/message catalogs.
- Dashboard-native decode widgets using canonical code values.
